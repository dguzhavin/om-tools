# Python SDK Optimacros: что он даёт бизнесу

Python SDK позволяет работать с моделью Optimacros из отдельной программы на Python. Такая программа
читает и записывает данные модели, меняет справочники, формулы и доступы, запускает скрипты.

Запускаться по расписанию и обмениваться данными с внешними системами умеют и встроенные скрипты
Optimacros, так что SDK нужен не для этого. Он нужен, когда вокруг модели хочется построить своё
приложение: другой интерфейс для пользователей, расчёт на библиотеках Python для анализа данных и
машинного обучения или инструмент, который смотрит на модель целиком, на её структуру, формулы и доступы.

## Что умеет

- **Данные.** Выгружать и загружать данные мультикубов, копировать их между мультикубами, очищать.
- **Справочники.** Создавать справочники, добавлять, переименовывать и удалять элементы.
- **Структура модели.** Показывать, какие в модели мультикубы, кубы, формулы и дашборды и что на
  каком дашборде лежит. Менять формулы.
- **Доступы.** Читать и менять права ролей и доступ пользователей к элементам справочников.
- **Скрипты.** Запускать скрипты модели, смотреть историю запусков и их код.
- **Обслуживание.** Пересчитывать модель, останавливать и запускать её, скачивать резервные копии.
- **Оптимизация.** Выгружать задачу оптимизации, чтобы решить её внешним солвером.

## Чего не умеет

Мультикубы, кубы и измерения через SDK не создаются, структуру модели по-прежнему строят руками.
SDK — инструмент разработчика: под каждую задачу кто-то пишет небольшую программу. Часть функций
пока работает с ошибками, у технической команды есть
[подробный справочник](https://github.com/dguzhavin/om-tools/blob/main/py-sdk-probe/os_ws_sdk_reference.md)
с обходными путями.

## Что можно сделать

1. **Своя форма ввода.** В Optimacros данные вводятся в мультикуб, то есть в таблицу с единой
   структурой заголовков. Если пользователям нужна одна таблица, где у первых колонок два уровня
   заголовков, а у остальных три, или просто понятная форма вместо грида, делаем свой веб-интерфейс.
   Введённые данные программа записывает в модель.
2. **Свои графики и отчёты.** Визуализации нужного вида, если стандартных не хватает. Данные берутся
   из модели напрямую, без промежуточных выгрузок.
3. **Тяжёлые расчёты вне модели.** Прогноз спроса на ML-модели, сегментация клиентов, статистика.
   Данные выгружаются из модели, считаются в Python, результат возвращается в модель и дальше
   участвует в планировании как обычные данные.
4. **Внешний оптимизатор.** Задача из модели уходит в специализированный солвер, например для
   производственного планирования. Возврат решения в модель мы сейчас прорабатываем.
5. **Отчёт по доступам.** Раз в неделю отдел безопасности получает таблицу: кто какие данные видит и
   может менять. Новому сотруднику права выдаются по шаблону роли одним запуском.
6. **Карта модели.** Схема, какой дашборд собран из каких мультикубов и какие формулы на что ссылаются.
   Видно, что сломается, если поменять куб, и новым людям проще разобраться в модели.
7. **«Откуда эта цифра?»** Нейросеть получает формулы и структуру модели и объясняет пользователю расчёт
   простыми словами. Тот же подход годится для проверки формул перед релизом.
8. **Проверка перед релизом.** Ключевые цифры снимаются до и после изменения модели и сравниваются
   автоматически. Если что-то поехало, это видно до того, как заметят пользователи.
9. **Свои резервные копии.** Бэкапы моделей регулярно скачиваются в хранилище компании.
