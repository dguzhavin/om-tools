# Python SDK Optimacros: что он даёт бизнесу

Python SDK позволяет работать с моделью Optimacros из отдельной программы на Python. Такая программа
читает и записывает данные модели, меняет справочники, формулы и доступы, запускает скрипты.

SDK нужен, когда вокруг модели хочется построить своё приложение: другой интерфейс для пользователей,
процесс согласования поверх модели, своё API для других систем, доступ к модели для AI-ассистентов,
расчёт на библиотеках Python для анализа данных и машинного обучения или инструмент, который смотрит
на модель целиком, на её структуру, формулы и доступы.

## Что умеет

- **Данные.** Выгружать и загружать данные мультикубов, копировать их между мультикубами, очищать.
- **Справочники.** Создавать справочники, добавлять, переименовывать и удалять элементы.
- **Структура модели.** Показывать, какие в модели мультикубы, кубы, формулы и дашборды и что на
  каком дашборде лежит. Менять формулы.
- **Доступы.** Читать и менять права ролей и доступ пользователей к элементам справочников.
- **Скрипты.** Запускать скрипты модели, смотреть историю запусков и их код.
- **Обслуживание.** Пересчитывать модель, останавливать и запускать её, скачивать резервные копии.
- **Оптимизация.** Выгружать задачу оптимизации, чтобы решить её внешним солвером.

## Чего не умеет

Мультикубы, кубы и измерения через SDK не создаются, структуру модели по-прежнему строят руками.
SDK — инструмент разработчика: под каждую задачу кто-то пишет небольшую программу. Часть функций
пока работает с ошибками, у технической команды есть
[подробный справочник](https://github.com/dguzhavin/om-tools/blob/main/py-sdk-probe/os_ws_sdk_reference.md)
с обходными путями.

## Что можно сделать

1. **Своя форма ввода.** В Optimacros данные вводятся в мультикуб, то есть в таблицу с единой
   структурой заголовков. Если пользователям нужна одна таблица, где у первых колонок два уровня
   заголовков, а у остальных три, или просто понятная форма вместо грида, можно сделать свой
   веб-интерфейс. Введённые данные программа записывает в модель.
2. **Свои графики и отчёты.** Визуализации нужного вида, если стандартных не хватает. Данные берутся
   из модели напрямую, без промежуточных выгрузок.
3. **Свой workflow вокруг модели.** Процесс из этапов и задач со статусами, ответственными, ролями и
   согласованиями. За основу берётся согласование документов, но так можно описать любой процесс.
   Например, бюджетный цикл: логистика вносит данные по своему блоку прямо в интерфейсе приложения или
   по ссылке в модели, отправляет на согласование и закрывает задачу. Приложение через права доступа
   закрывает ввод по блоку логистики, и процесс идёт к следующему шагу. Ответственным приходят
   уведомления и напоминания. По логике это похоже на сервис Optimacros
   [OptiFlow](https://optiflowsoft.ru/), только собранный под конкретный процесс клиента и доработанный
   там, где готовой функциональности не хватает.
4. **Тяжёлые расчёты вне модели.** Прогноз спроса на ML-модели, сегментация клиентов, статистика.
   Данные выгружаются из модели, считаются в Python, результат возвращается в модель и дальше
   участвует в планировании как обычные данные.
5. **Внешний оптимизатор.** Задача из модели уходит в специализированный солвер, например для
   производственного планирования. Далее результат возвращается обратно в модель.
6. **Отчёт по доступам.** Раз в неделю отдел безопасности получает таблицу: кто какие данные видит и
   может менять. Новому сотруднику права выдаются по шаблону роли одним запуском.
7. **Карта модели.** Схема, какой дашборд собран из каких мультикубов и какие формулы на что ссылаются.
   Видно, что сломается, если поменять куб, и новым людям проще разобраться в модели.
8. **«Откуда эта цифра?»** Нейросеть получает формулы и структуру модели и объясняет пользователю расчёт
   простыми словами. Тот же подход годится для проверки формул перед релизом.
9. **AI-ассистент с доступом к модели.** MCP — стандарт, через который AI-ассистенты (Claude, ChatGPT,
   корпоративные агенты) подключаются к внешним системам. MCP-сервер на базе SDK даёт ассистенту
   доступ к модели в рамках выбранных действий. Пользователь пишет в чате «сколько осталось бюджета по
   отделу» или «пересчитай прогноз», и ассистент сам находит данные или запускает нужный скрипт.
10. **Проверка перед релизом.** Ключевые цифры снимаются до и после изменения модели и сравниваются
    автоматически. Если что-то поехало, это видно до того, как заметят пользователи.
11. **Свои резервные копии.** Бэкапы моделей регулярно скачиваются в хранилище компании.
12. **Уведомления о сбоях.** Скрипт упал ночью, и утром команде приходит сообщение в Telegram, а не
    звонок от пользователя.
13. **Своё API к модели.** Встроенные скрипты сами ходят во внешние системы по расписанию. Здесь
    наоборот: поверх SDK делается небольшой сервис, и другие системы обращаются к модели сами, в момент
    события на своей стороне. CRM при закрытии сделки сразу добавляет её в прогноз продаж, портал
    закупок проверяет остаток бюджета перед согласованием заявки.
